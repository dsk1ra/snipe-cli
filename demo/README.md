# snipe TUI demo

![snipe TUI hero loop](snipe-hero.gif)

Two recordings and a gallery, all built from the same fixture:

| what | file | for |
|---|---|---|
| hero loop, ~35 s | `snipe-hero.gif` | the top of the root README — it autoplays, so it has one loop to make its case |
| walkthrough, ~3:45 | `snipe-demo.mp4` | linked, not embedded: the `/` palette, the queue and its row actions, the report reader from two tabs, the P1 gate, a run paused and resumed, a pasted JD, the heatmap and the follow-up board |
| stills | `screens/*.png` | the README gallery |

`palette.png` · `queue.png` · `report.png` · `running.png` ·
`activity-year.png` · `activity-day.png` · `followups.png` · `keys.png`

**Nothing in it is real.** The companies, roles, scores, applications and
follow-ups are generated by `sandbox/seed.go`, and the pipeline behind them is
`sandbox/sim.go` — a stand-in that writes the files the real pipeline writes, on
a timer. No model runs, no posting is fetched, `cv.md` is never read, and the
real `data/` tree is never opened.

## Recording it

```bash
bash demo/record.sh                 # all three, ~10 min
bash demo/record.sh hero            # or one: hero | walkthrough | screens
```

Each is seed → record → caption, and each re-seeds first:

```bash
go build -o demo/.sandbox.bin ./demo/sandbox
./demo/.sandbox.bin seed -o demo/.sandbox     # build the fixture
mv demo/.sandbox.bin demo/.sandbox/snipe      # the binary lives in it
vhs demo/snipe.tape                           # → demo/.sandbox/raw-demo.mp4
go run ./demo/caption demo/snipe.tape         # burn captions → demo/snipe-demo.mp4
```

Needs [vhs](https://github.com/charmbracelet/vhs), which needs `ttyd` and
`ffmpeg`. No package manager required:

```bash
curl -sL https://github.com/charmbracelet/vhs/releases/download/v0.11.0/vhs_0.11.0_Linux_x86_64.tar.gz \
  | tar xz -C /tmp && install -m755 /tmp/vhs_0.11.0_Linux_x86_64/vhs ~/.local/bin/vhs
curl -sL -o ~/.local/bin/ttyd https://github.com/tsl0922/ttyd/releases/download/1.7.7/ttyd.x86_64 \
  && chmod +x ~/.local/bin/ttyd
```

Re-seeding is not optional: each tape drives a session that mutates the sandbox
(queues offers, runs them, marks one applied, nudges a follow-up), so a second
run against a used sandbox starts from a different screen and the fixed sleeps
drift out of step with it.

`hero.tape` sets `DEMO_SPEED=0.45`, which scales every phase duration in
`sim.go` — the same run, short enough to loop.

## How the sandbox works

`demo/sandbox` is one binary that is three things:

| invoked as | what it does |
|---|---|
| `snipe seed -o demo/.sandbox` | writes the whole fixture: a year of evals, reports, `output/` folders, the tracker, today's queue |
| `snipe` | the **real** TUI — `internal/tui`, unmodified — pointed at the fixture |
| `snipe run …` | the fake pipeline: the same files, the same state transitions, on a timer |
| `snipe scan` | the fake portal sweep: the same counters, two invented finds, queued. This is what `/scan` runs — the palette re-executes the binary it is already running |

The TUI resolves both of its roots from `os.Executable()`, and spawns its runner
by re-executing that same path with `run …`. So a binary sitting in
`demo/.sandbox` drives the sandbox and can reach nothing else — no `SNIPE_HOME`,
no copied source, no stubbed module resolution. `xdg-open` and `notify-send` are
`bin/` stubs on `PATH` that log and do nothing, so a recording never has a file
manager thrown over it.

What the fake runner reproduces, because the demo turns on it:

- **The lock.** `state.Acquire`, held for the whole run, so ▶ becomes a spinner
  and `s` / `p` have something to signal.
- **Checkpoints.** Each phase naps through the same stages the real one
  checkpoints (`p1.fetch`, `p2.jdparse`, `p2.evidence`, `p2.judgment`,
  `p3.select`, `p3.render`), marking one in flight before the nap and clearing it
  after. That is what makes `p` say *which* model call it dropped, and what makes
  the resume redo that one and no more.
- **The queue, popped one id at a time**, pushed back on a stop — a queue emptied
  up front takes every waiting row off the screen at once.
- **The tracker**, through the real `tracker.Merge` over a real addition file.

The sandbox implements `scan` and `run` only, so `/doctor` and `/status` come
back as its usage line rather than a report. Neither is in a tape.

Each offer's outcome is decided before it runs, in `demo/.sandbox/plan.json` —
which is what makes the tape's sleeps line up with the phases. An offer with no
plan entry is a JD pasted into the TUI moments ago: `sim.go` reads its first line
for the company and role, so the Helix Systems row in the recording comes from
the text that was pasted, not from a lookup table.

**One deliberate divergence from production:** the demo runs each offer through
all three phases before starting the next (`p1→p2→p3`, then the next offer).
`internal/run` batches by phase instead — Phase 1 across every offer, then Phase
2 — which is right when each phase loads a different model, but on screen leaves
every row half-finished until the very end.

The seed also holds each heatmap to a single gold cell: gold means "busiest day",
and two of them read as a rendering bug. One weekday is given more scans than the
cap every other day is held to, and its offers are forced past the Phase 1 gate —
a gated offer writes no eval, and the heatmap counts evals. Application ties are broken
afterwards, since those counts are a by-product rather than a plan.

## Captions

VHS has no caption command, so `demo/caption` pads the frame and draws the text
into a strip below the terminal with ffmpeg — nothing the TUI drew is covered.

The captions live in the tape itself, as `#>` comment lines above the keystroke
they describe (`#>` alone clears the strip). `caption` re-walks the tape and adds
up what each command costs — a `Sleep` is its own duration, a `Type` is one
`TypingSpeed` per character, a key press is one — then scales that timeline onto
the recording's real duration to absorb VHS's per-keystroke overhead. The model
lands within a second over three minutes, and more usefully, a caption cannot
drift away from the action: moving a cue in the tape moves it in the video.

## Editing the tape

- **The focus model is the tape.** There is no global cursor: `tab` cycles
  inputs ⇄ ▶ ⇄ list, `↓` drops into the list at the newest row, `esc` steps back
  out. Which keys reach ▶ therefore depends on where the previous scene left off
  — from the list it is `Tab Tab Enter`, from the JD box one `Tab`. Get it wrong
  and Enter fires whatever else was focused.
- **`←` and `→` fall through at a row's edges.** Walking off the last inline
  action switches *tab*, because a row with no actions has always done that.
  Count the actions on the row you are on: a finished row has two (report, link),
  a gated one two (proceed?, link), a failed one three (see error, retry, debug).
- **`Paste` is not a paste.** VHS sends the clipboard as individual keystrokes
  with no bracketed-paste markers, so the JD box has to be focused *first* or the
  text is read as hotkeys. It also means the tape cannot demonstrate the paste
  router — a link pasted into the JD box only moves itself to the URL field on a
  real `tea.PasteMsg`, which VHS never sends.
- **`/` is the palette, not a key.** It borrows the JD box for a one-line prompt
  and runs one of this binary's own subcommands, so a tape drives it as
  `Type "/"`, `Type "scan"`, `Enter` — and the output arrives in the reader
  pane, which `esc` closes like any other. A tape can also just focus the JD box
  and type the whole command: a field holding nothing but `/name` runs on Enter
  rather than walking on to ask for a URL.
- **The reader pane is borrowed, and it takes the tab with it.** `v` on a row,
  "see error", and `o` on the follow-ups board all open the same pane, which is
  drawn on the queue tab — so opening one from the follow-ups board switches
  tabs, and `esc` switches back. A tape that counts tabs has to count those two.
- **A single key can belong to two tabs.** `p` is pause globally and "proceeded"
  on the follow-ups tab, which owns it first; on the queue tab it only pauses
  while nothing is being typed into. The tape presses `esc` before `p` for
  exactly that reason.
- **`r` starts a five-second grace timer** before the rejection is written, so
  the `u` that undoes it has to land inside the window. Keep that pair short.
- **`Wait+Screen` does not match the footer**, so timing is fixed `Sleep`s
  against the phase durations at the top of `sim.go`. Change one and the other
  needs a look.
- **`Screenshot` fires at the start of the next command**, so every one in
  `screens.tape` is followed by a `Sleep`. Without it the shot lands a keypress
  late, which is how a "queue" screenshot comes out showing the Activity tab.
- Absolute paths in a tape fail to parse if they contain digits and dashes — run
  `vhs` from the repo root and keep the paths relative.
- Caption text goes through ffmpeg's `textfile=`, not the filter string: `:`, `'`
  and `,` are all filter syntax, and escaping them by hand is how a caption ends
  up silently truncated at its first colon.
